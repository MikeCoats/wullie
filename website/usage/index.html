Using Wullie

Wullie never changes your files itself. It prints a patch, and you decide whether to apply it.

Running Wullie

Run wullie with the folder to search, or with no folder to search the current one:

wullie ~/code/my-project

Wullie searches that folder, and every folder inside it, for Cargo.toml, pyproject.toml and package.json files. It looks up every dependency they list, and prints one unified diff that pins each out-of-date dependency to its latest release. The paths in the diff are relative to the folder you searched.

The diff goes to standard output, and any warnings go to standard error, so you can redirect the diff to a file: 

wullie ~/code > deps.patch

Applying the changes

From the root of a git repository, pipe the diff straight into git apply:

wullie | git apply

Outside git, patch -p1 < deps.patch does the same job. Either way, review the changes with git diff before you commit them.

Wullie only changes manifests. It doesn't install packages or touch lock files, so afterwards regenerate and commit Cargo.lock, uv.lock, package-lock.json or the equivalent, then run your tests.

Wullie pins to the newest release even when that's a new major version, which may have breaking changes. If you're not ready for one, edit that line before you apply the patch.

What gets checked

A dependency is out of date when the oldest release its requirement allows is older than the latest release. So ^1.2 is out of date as soon as 1.3 is out, even though it would allow 1.3. A requirement with no version at all, or one like * or latest, is always out of date.

Every kind of dependency is checked: normal, development, build and optional dependencies alike. Yanked releases, deprecated npm versions and pre-releases are never suggested, unless a requirement already asks for a pre-release.

Ecosystem Pinned as Left alone
Rust, from crates.io =1.2.3 Dependencies with registry, registry-index, path or git, or with workspace = true
Python, from PyPI ==1.2.3 Direct references, such as name @ https://…. Extras and environment markers are kept.
JavaScript, from npm 1.2.3 Local paths, git repositories, URLs and workspaces. npm: aliases are checked under the package they point to.

If a manifest can't be read, Wullie warns about it and skips the whole manifest rather than giving you a partial answer.

What gets skipped

Wullie respects .gitignore and other standard ignore files, and skips hidden folders. It also skips build, cache and dependency folders, in every project, whichever ecosystem they belong to:

  • target/
  • __pycache__/, __pypackages__/ and site-packages/
  • node_modules/ and bower_components/

Symbolic links are skipped too, whether they point to a manifest or a folder, so Wullie never leaves the folder you asked it to search.

Caching and --refresh

Wullie caches every registry lookup for four hours, so running it again, or over many projects that share dependencies, doesn't repeat thousands of requests. The cache is in your platform's usual place for caches:

  • Linux: ~/.cache/wullie, or $XDG_CACHE_HOME/wullie if you've set that
  • macOS: ~/Library/Caches/xyz.mikecoats.wullie, or $XDG_CACHE_HOME/wullie if you've set that
  • Windows: %LOCALAPPDATA%\MikeCoats\wullie\cache, usually C:\Users\<username>\AppData\Local\MikeCoats\wullie\cache

If a release came out since your last run, such as an urgent security fix, ignore the cache and look everything up again: 

wullie --refresh

Exit codes

Exit code Meaning
0 Every manifest was checked, regardless of whether any updates were found.
2 Something went wrong, or part of the tree couldn't be checked, so the diff may be incomplete. The warnings say what.

Using with CI

For Wullie, finding updates isn't an error, so a CI job that should fail on out-of-date dependencies needs to actually check whether the diff is empty: 

patch=$(wullie) || exit 2
if [ -n "$patch" ]; then
    printf '%s\n' "$patch"
    exit 1
fi

The job will then fail if any dependencies are out of date, and the log will show the diff that would fix the CI run.
